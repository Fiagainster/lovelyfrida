# 02 · 总体架构

---

## 一、技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 应用外壳 | **Tauri 2.x** | 单 exe 分发、Rust 后端能做进程控制、Web 前端能做复杂可视化。与开发者的 Rust/Tauri 经验一致 |
| 后端语言 | **Rust**（stable，edition 2021+） | 进程/PTY/并发是它的强项；无 GC，长跑日志流不抖 |
| 前端 | **Vue 3 + Vite + TypeScript** | 组件化适合「多视图切换」；比 React 上手成本低，够用 |
| 代码编辑器（探针 JS） | **Monaco Editor** | 与 VS Code 同源，语法高亮/补全/错误提示开箱即用 |
| 终端 | **xterm.js** + Rust `portable-pty` | 「原始终端」视图（原则 2 的最底层） |
| 图表 | **ECharts** | 时间轴、差分矩阵热力、性能曲线的可视化 |
| 本地库 | **SQLite**（Rust `rusqlite`，bundled） | 档案/trace 持久化；单文件、可备份、可交给别人 |
| 状态管理（前端） | **Pinia** | 与 Vue 3 原生配套 |
| 导出加密 | **age**（可选） | 导出含密钥的档案时可加密 |

**明确不用**：Electron（体积与内存不划算）、任何需要联网的组件。

**一条纪律**：所有对设备的操作必须经过 `AdbBackend`，所有对 frida 的操作必须经过 `FridaBackend`。任何绕过这两个 trait 的直接调用都视为架构违规 —— 因为**只有在这两层里，超时、幂等、只读、记录才知道自己在被使用**。

## 三、Frida 三通道设计（本文档最关键的部分）

### 3.1 为什么需要三条

frida 生态的版本耦合是硬伤（原则 6 / 痛点 S1）。只押一条通道，等于把整个工具的可用性绑在某个库的版本上。

| 通道 | 实现 | 优点 | 代价 | 用途 |
|:--:|---|---|---|---|
| **A** | Rust `frida` crate（in-process 绑定 frida-core） | 结构化消息、低延迟、单 exe 分发、无需外部运行时 | 编译期耦合 frida-core 版本；构建较重 | **默认通道** |
| **B** | Python sidecar（`frida` 官方绑定），JSON-RPC over stdio | 与设备端版本解耦，可随时升降；已实测可用（16.7.19） | 需随包带 Python 运行时 | **兼容通道**（A 不可用时自动切换） |
| **C** | CLI 子进程（`frida.exe -l agent.js`），流式解析 | 永远可用；输出就是"别人看到的原始样子" | 无结构化，只能解析文本 | **逃生通道 + 原始终端视图** |

三通道对上层暴露**同一个 trait**：

| 方法 | 语义 |
|---|---|
| `devices()` | 枚举设备 |
| `processes()` | 枚举进程 |
| `spawn(pkg)` / `attach(target)` | 起/挂 |
| `load(agent_src, opts)` | 注入 agent，返回句柄 |
| `post(handle, msg)` | 宿主 → agent 双向调用 |
| `messages(handle)` | 事件流（结构化 JSON） |
| `detach(handle)` | 卸载并清理 |

### 3.2 核心决策：结构化来自 Agent，不是解析 stdout

这是整个架构里最重要的一条：

> **所有通道都跑同一份 agent 脚本，agent 用 `send()` 回传 JSON。宿主只做 JSON 解析，从不解析控制台文本。**

```
agent.js  ──send({t:"call", cls, m, args, ret, ts, thread})──▶  宿主
                                                                  │
                                                    TraceEvent ◀──┘  （直接落库/上屏）
```

为什么不让宿主去正则解析 `IN=... OUT=...`？因为：

- 文本解析必然脆弱（参数里含空格、含换行、含 `||` 分隔符就崩）
- 参数是**结构化对象**（byte[]、String、对象引用），压成字符串就丢了类型
- 一旦丢类型，后面**差分矩阵**和**算法还原**就没有可靠输入

所以「探针工作台」的职责是：**把用户的可视化配置编译成 agent.js**，而不是拼 console.log 字符串。

### 3.3 通道切换策略

```
启动自检
  ├─ 通道 A 可用（内置绑定与设备端 server 版本匹配）?  → 用 A
  ├─ 否则 通道 B 可用（sidecar 启动 + frida 模块 import 成功）? → 用 B
  └─ 否则 → 用 C，并明确提示：结构化能力降级，Trace 为文本形态
```

切换过程必须**在 UI 上说出来**（原则 1：状态可见）。不允许静默降级。

## 四、ADB 层设计

### 4.1 不解析文本，用「命令 + 状态谓词」

| 需要知道的事 | 命令 | 通过判据 |
|---|---|---|
| 有哪些设备 | `adb devices -l` | 输出含 `<serial> device` |
| 是否 root | `adb -s <s> shell id` | 含 `uid=0(root)` |
| SELinux 模式 | `getenforce` | `Permissive` / `Enforcing` |
| 架构（决定推哪个 frida-server） | `getprop ro.product.cpu.abi` | `x86_64` / `arm64-v8a` |
| 应用 uid | `pm list packages -U` | 正则抓 `uid:(\d+)` |
| server 是否真在监听 | `ss -tlnp` | 含 `:27042` |
| 回灌文件是否一致 | `md5sum <path>` | 与本地值相等 |

### 4.2 三条硬性策略（全部来自痛点）

| 策略 | 依据 |
|---|---|
| `adb connect` **必须**带 15s 硬超时 | E2：连到非 adbd 端口会无限挂死 |
| 每次操作前先清残留（`disconnect` / `pkill -f frida-server`） | S3：旧进程不会自己死；脚本必须幂等 |
| `offline` 走自愈重试曲线（2s × 5 次） | E4：模拟器刚起时 adbd 未就绪 |

### 4.3 命令构造要分 shell 方言

同一件事在 PowerShell 与 bash 里写法不同（D4：`mkdir -p a/{b,c}` 在 PS 里跑不通）。命令渲染层按目标 shell 出两套模板：

| 用途 | 设备端（sh） | 本机 bash | 本机 PowerShell |
|---|---|---|---|
| 建多级目录 | 一条一条写，避免依赖花括号 | 可用花括号 | 一条一条写 |
| 多命令串联 | `su -c 'cmd1; cmd2'`（**只能单引号**，D3） | `cmd1 && cmd2` | `cmd1; cmd2` |
| 环境变量 | 设备端不存在于宿主 | `$VAR` | `$env:VAR` |

UI 上「复制为命令」按钮默认给**当前用户的操作系统**那套。

## 五、会话状态机

```
IDLE
 └─▶ DISCOVERING ──▶ DEVICE_READY ──▶ APP_INSTALLED ──▶ DATA_INJECTED
                          │                  │                 │
                          │                  │                 ▼
                          │                  │            SERVER_UP
                          │                  │                 │
                          │                  │                 ▼
                          │                  │            FORWARDED
                          │                  │                 │
                          └──────────────────┴─────────────────┴──▶ ATTACHED
                                                                       │
                                                            ┌──────────┴──────────┐
                                                            ▼                     ▼
                                                         RUNNING ◀──▶ PAUSED   STOPPED
```

| 状态 | 前置条件 | 探测 | 失败时用户看到 |
|---|---|---|---|
| `DISCOVERING` | 模拟器/真机已启动 | 端口扫描 + `adb connect`（超时） | 试过的端口列表 + 每个的结果 |
| `DEVICE_READY` | 设备 `device` 状态 | `id` / `getenforce` / `abi` | 是否 root；非 root 时给 `adb root` 建议 |
| `APP_INSTALLED` | APK 路径有效、签名不冲突 | `pm list packages -U` | 冲突时给 `uninstall` 步骤 |
| `DATA_INJECTED` | 本地数据目录存在 | `md5sum` 逐个对比 | 哪个文件不一致 + 哪一步（chown/restorecon）没做 |
| `SERVER_UP` | frida-server 二进制版本匹配 | `ss -tlnp` | 三处版本对照表 |
| `FORWARDED` | 设备端在监听 | `adb forward --list` | forward 表 + 建议 |
| `ATTACHED` | 目标进程存在 | `frida-ps` 能列出 | 包名候选（含拼写建议） |
| `RUNNING` | agent 已注入 | agent 首条 `send({t:"hello"})` | 注入失败原因 |

**关键**：任一状态可失败，但**状态机不回退** —— 失败保留在当前位置，现场不清空，用户可只重试该步。理由是动态分析里"前面明明成功了"是重要信息（可能只是设备重启）。

## 六、进程与线程模型（Rust）

| 关注点 | 设计 |
|---|---|
| 异步运行时 | `tokio`（多线程） |
| 设备访问串行化 | 每台设备一个 **DeviceActor**（单任务队列）。避免并发 adb 命令互相踩 |
| 子进程监管 | 每个子进程（adb / frida CLI / Python sidecar）一个 supervisor task：负责启动、读流、超时、退避重启、退出清理 |
| 事件分发 | `tokio::sync::broadcast` → Tauri event → 前端。日志量大，需**背压**（丢弃策略：保留结构化事件，原始日志超限时降采样） |
| PTY | `portable-pty`，用于「原始终端」视图，与可视化操作**共享同一个 adb server** |
| 取消 | 所有长操作接受 `CancellationToken`；取消 = 清理现场，不是留着半截 |
| 阻塞调用 | `rusqlite` 与重哈希计算放 `spawn_blocking`，不占 async 线程 |

### 事件分层（决定前端卡不卡）

| 层 | 内容 | 频率 | 传输 |
|---|---|---|---|
| L1 状态 | 状态机迁移、探针装载/命中计数 | 极低 | 全量推送 |
| L2 结构化 Trace | 每次调用的 args/ret（已格式化） | 中高（可能上千/秒） | 批量 + 前端虚拟滚动 |
| L3 原始输出 | stdout/stderr 全文 | 极高 | **按需拉取**（默认只留在环形缓冲，前端打开终端时才流） |

依据：O2 的教训 —— 日志炸开会把工具本身搞得不响应。

## 七、错误处理与重试

| 类型 | 策略 |
|---|---|
| 瞬时（offline、通道抖动） | 指数退避重试，上限 5 次，每次都记进事件流 |
| 可恢复（forward 丢失、server 被杀） | 自动重建，**但在 UI 上明确标注"已自动恢复"**，不静默 |
| 配置性（版本不匹配、端口错） | 不重试；直接进诊断知识库，给处置动作 |
| 致命（检材路径写失败、设备掉线） | 停止流水线，保留现场，冻结后续步骤 |

## 八、存储与路径（不写 C 盘）

**默认全部落在项目目录**，不写 `%APPDATA%`、不写任何系统盘路径：

```
D:\Project\lovelyfrida\
├── bin\                     # 内置二进制
│   ├── adb\                 # 与模拟器版本对齐的 adb
│   └── frida-server\        # 矩阵：<version>\<abi>
├── workspace\               # ★ 唯一可写区；从检材复制来的工作副本
│   └── <case>\<app>\
├── cases.db                 # SQLite：档案、trace、实验、结论
├── logs\                    # 运行日志（含审计日志）
├── exports\                 # 导出的 markdown / 报告 / 截图
└── config.toml              # 路径、端口、默认通道、脱敏策略
```

`config.toml` 支持把 `workspace` 改到别的盘（大案子的工作副本可能很大），但**默认不给系统盘**。

## 十、版本兼容矩阵

| frida 客户端 | 时序特征 | 工具对策 |
|---|---|---|
| 16.x | 类加载较快，`Java.perform` 通常可立即执行 | 正常注册 |
| 17.x | 类加载更慢，早期 hook 会失败 | **自动延迟注册 + 失败重试**（替代手写 `setTimeout(...,3000)`，痛点 P2） |

| 目标 ABI | frida-server 包 | 备注 |
|---|---|---|
| `x86_64` | `frida-server-<v>-android-x86_64` | 模拟器（本轮实测环境） |
| `arm64-v8a` | `frida-server-<v>-android-arm64` | 真机 / Apple Silicon 模拟器 |
| `x86` / `armeabi` | 已基本淘汰 | 只做提示，不预置 |

**风险登记**：通道 A 依赖的 `frida` crate 若长期落后于设备端 frida-server，则以通道 B 为主。这个切换应该是**配置项**，不是硬编码分支。

## 十一、可扩展点（留给以后）

| 扩展 | 接口 |
|---|---|
| 新探针模板（如 r0capture 风格抓包） | 模板包（声明式 + 可选 JS 片段） |
