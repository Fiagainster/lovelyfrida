# 03 · 可视化交互设计

> 本文档回答一个问题：**Frida 的每一步，用什么形状画出来最省脑子？**

---

## 一、整体布局

```
┌───────────────────────────────────────────────────────────────────────────┐
│ 顶栏  ◆ 案子: 盘古石杯/韦明辉-notevault   通道A ●  版本三处一致 ✓  只读锁 🔒 │
├──────────┬────────────────────────────────────────────┬───────────────────┤
│ 流水线    │  主工作区                                   │  详情 / 诊断       │
│ (左导航)  │  ┌──────────────────────────────────────┐  │  ┌─────────────┐  │
│          │  │  六个视图切换                          │  │  │ 诊断卡片     │  │
│ ● 环境    │  │  流水线│时间轴│差分│拓扑│终端│档案       │  │  │ ⚠ 探针零命中  │  │
│ ● 连接    │  ├──────────────────────────────────────┤  │  │  原因…       │  │
│ ● 装载    │  │                                      │  │  │  [执行处置]  │  │
│ ● 回灌    │  │          （视图内容）                  │  │  └─────────────┘  │
│ ○ 探针    │  │                                      │  │  ┌─────────────┐  │
│ ○ 观测    │  │                                      │  │  │ 等价命令     │  │
│ ○ 还原    │  │                                      │  │  │ [复制] [终端]│  │
│ ○ 归档    │  └──────────────────────────────────────┘  │  └─────────────┘  │
├──────────┴────────────────────────────────────────────┴───────────────────┤
│ 底栏  就绪  ·  探针 3 装载 / 0 命中  ·  事件 12.4k/s  ·  ⌘K 命令面板  [终端 ▲] │
└───────────────────────────────────────────────────────────────────────────┘
```

三条布局上的主张：

1. **左栏是流水线而不是菜单** —— 用户永远知道「现在在哪一步、下一步是什么」，这是痛点台账里 33 条坑的形态解药。
2. **右栏永远在讲「为什么」** —— 诊断卡片 + 等价命令，是设计原则 1 和 2 的落点。
3. **终端是可升降的抽屉，不是独立窗口** —— 因为它属于每个视图，不属于某一个视图。

## 二、六种视图

### 视图 1 · 流水线（主视图）

```
 ● 环境体检 ──── ● 设备连接 ──── ● 应用装载 ──── ◐ 数据回灌 ──── ○ 探针注入 ──── ○ 观测 ──── ○ 还原 ──── ○ 归档
   ✔ 4/4          ✔ 3/3          ✔ 2/2          ⏱ 2/5           —              —            —            —
   adb 来源       端口 16385      uid 10042      文件 1/4 中
   frida 16.7.19  root ✓          签名 ✓          ▸ 卡在 push
```

每个节点：**状态灯 + 子项计数 + 一行摘要**。点开节点 → 展开该步的**逐条检查项**（每项独立状态灯，因为「部分成功」是最常见也最容易被忽略的形态）。

节点展开后长这样：

```
 ◐ 数据回灌                                     [重试本步] [复制命令] [开终端]
   ✔ 停应用       am force-stop com.notevault.app
   ✔ 空跑建档     monkey -p com.notevault.app ...
   ✔ 建目录       3 个目录已存在
   ⏱ 推送文件     1/4  · 卡在 notevault.db
   ○ 改属主       chown -R 10042:10042 ...
   ○ 刷标签       restorecon -R ...
   ○ 校验         md5sum 对比
   ┌ 诊断 ────────────────────────────────────────────────────┐
   │ ⚠ push: Permission denied                                 │
   │ 真因：adbd 非 root 或目标目录属主不符                       │
   │ 处置：① adb root 重连 ② 或走 /data/local/tmp 中转 + su -c  │
   │ [执行处置①]  [执行处置②]  [看规则 D2]                       │
   └───────────────────────────────────────────────────────────┘
```

**为什么逐条而非整步**：因为痛点 D1 的本质是「四步里漏了第三、四步」，整步显示"失败"会让人以为是第一步错了。

### 视图 2 · 时间轴（探针触发流）

```
 时间      类别   目标                            入参                          返回                     线程  耗时
 ─────────────────────────────────────────────────────────────────────────────────────────────────────────

 12.058   ARG    SQLiteDatabase.<init>[1]        byte[14]="ABCDEFGHIJKLM"          —                 m  0.1ms  ⚑

 ─────────────────────────────────────────────────────────────────────────────────────────────────────────
 筛选: [类名…] [仅命中 ⚑] [方法 ▾]   分组: [按方法 ▾]   显示 4 / 4    [导出 CSV] [导出 JSON]
```

能力清单：

| 能力 | 说明 |
|---|---|
| 列可裁剪 | 参数多的时候，只保留关心的列 |
| 同方法对比 | 选中两次调用 → `对比` 打开左右并排差异 |
| 序列导出 | 一键变成「第 1 次：入参… → 返回…」，可直接粘进笔记（O5） |
| 参数下钻 | 点 `byte[14]` 展开完整 hex / 点对象展开字段表 |
| 虚拟滚动 | 十万条不卡（对应 02 的 L2 批量 + 虚拟列表） |
| 暂停/续灌 | 观测期间可暂停刷新（现场仍在缓冲），不丢数据 |

### 视图 3 · 差分矩阵（受控实验的核心）

这是全工具最有"产品味道"的一屏。**它的任务是把"规则"从数据里逼出来。**

场景：APK-15 要证明「真口令 = `password.json` 内容的 `[1:-2]`」。

```
  实验: password.json 内容 → SQLCipher 实际收到的口令
 ┌──────────────────────┬──────────────────┬──────────────┬────────────┬──────────────────────────┐
 │ 输入组（自造文件内容） │ 观测通道1         │ 通道2         │ 通道3       │ 变异度                    │
 │                      │ $init 收到的 byte[]│ mPassword 字段│ 开库是否成功 │                          │
 ├──────────────────────┼──────────────────┼──────────────┼────────────┼──────────────────────────┤
 │ ▶ XABCDEFGHIJKLMNO   │ "ABCDEFGHIJKLM"  │ "ABCDEFGHIJKLM"│ ✗         │ ★ 长度 16→14 (−2)         │
 │ PABCDEFGHIJKLMNOII   │ "ABCDEFGHIJKLM"  │ "ABCDEFGHIJKLM"│ ✗         │ ★ 同上（首末被削）        │
 │ ▷ abcdefgh           │ "bcdef"          │ "bcdef"      │ ✗          │   长度 8→5 (−3)           │
 │ ▷ abcde              │ "bcd"            │ "bcd"        │ ✗          │   长度 5→3 (−2)           │
 │ ▷ Pgs-ll20260423II   │ "gs-ll20260423"  │ "gs-ll20260423"│ ✔         │ ★★ 命中：−2 且可开库      │
 └──────────────────────┴──────────────────┴──────────────┴────────────┴──────────────────────────┘
   ▌结论候选（自动生成，待人工确认）
   ▌  ① 首字符被丢弃、末 2 字符被丢弃 → 变换 = [1:-2]      （4/4 支持）
   ▌  ② 长 16 与长 8 均削 2 尾 → 否证"丢固定 2 个尾字符"  （长度 8 时实际削 3）
   ▌  [确认此结论] [追加输入组验证] [全部导出]
```

三条设计要点：

| 要点 | 为什么 |
|---|---|
| **变异度列自动计算并排序** | 人眼找"哪一列不一致"很累；机器擅长 |
| **结论是"候选"不是"判决"** | 工具给证据，人给结论。有些规律会**自相矛盾**（上例中"削 2 尾"被长度 8 的行否证），必须暴露出来而不是吞掉 |
| 输入组带 `▶/▷` 标记 | 区分"自动生成"与"手工指定"，手工的那条通常最值钱 |

**追加输入组**这个动作是刻意设计的：第一次实验往往设计得不严谨，用户应该能**顺手补一组**去否证自己刚才的结论（原则 5 双证据的交互实现）。

把 "什么文件 → 经过什么变换 → 变成什么 → 用来解锁什么" 画成一张图。用途：**一眼看出断在哪**。

```

                    ┌─────────────────────┐        ┌─────────────────────┐
                    │ shared_prefs xml     │        │ notevault.db         │

                               │              │            （APK 内常量，尚未记录在案）

                    ┌─────────────────────┐   │
                    │ h₁=SHA256(明文‖salt) │   │
                    │ → 链式 ×10000        │   │
                    └──────────┬──────────┘   │
                               ▼              │
                    ┌─────────────────────┐   │
                    │ hex(h₁₀₀₀₀)          │   │
                    │ 1Q0Tvj9/…cUc=        │   │
                    └──────────┬──────────┘   │
                               │ 爆破 (hashcat -m 1410)
```

图上两种标记必须有：

| 标记 | 含义 | 上例 |
|---|---|---|
| ⚠ 空心虚线圈 | **断链**：已知存在但来源/去处未明 | `NoteVault_DB_SecureKey_2024` 的来源还没定位 |
| ✔ 实线 | 有实测证据支撑的边 | 明文‖salt → SHA-256 |

**这张图的价值在"⚠"**：它把「我们有一件事没搞清楚」变成界面上一个显眼的圈。项目里最有价值的待办，往往就是这些圈。

### 视图 5 · 原始终端

直接连 adb / frida 会话的 PTY。用途三条：

1. **看原始样子**（设计原则 2 的最底层）
2. **手试**：不确定的命令先在这里敲
3. **兜底**：可视化路径失败时，人还能干活

终端不是"另一个世界"：**在终端里手敲的命令会被 Recorder 记录**，可以一键"提升为流水线步骤"。

## 三、状态语义（全场统一）

### 状态灯

| 灯 | 状态 | 语义（必须能自证） |
|:--:|---|---|
| ○ 灰 | 未开始 | — |
| ◐ 蓝（脉冲） | 进行中 | 显示进度（3/7）与已耗时 |
| ● 绿 | 通过 | **必须伴随一条实测证据**（不能是"命令没报错"） |
| ◑ 黄 | 警告 | 通过但有隐患，或已降级（如通道 A→C） |
| ✖ 红 | 失败 | 必须伴随诊断卡片 |
| ⊘ 空 | 跳过 / 不适用 | 需说明为什么跳过 |

**「绿 = 有证据」是本设计的核心约束。** 反例在痛点台账里到处都是：S5（以为在监听）、O3（以为钩子生效）、D1（以为灌好了）。灯的绿色必须由**探测结果**点亮，不能由**命令返回码**点亮。

### 术语表（界面用词统一）

| 术语 | 定义 |
|---|---|
| **目标 (Target)** | 一台设备 + 一个应用 + 一份数据版本 的绑定 |
| **会话 (Session)** | 目标与一组探针的一次绑定 |
| **探针 (Probe)** | 声明式的挂钩定义（类 / 方法 / 参数格式化 / 命中条件 / 动作） |
| **运行 (Run)** | 会话的一次执行 |
| **轨迹 (Trace)** | 运行产生的结构化调用序列 |
| **实验 (Experiment)** | 一组受控输入 + 观测通道 + 差分结果 |
| **规格书 (Scheme)** | 从观测反推出的算法描述（可生成验证代码与爆破器骨架） |
| **任务 (Job)** | 一次爆破/枚举的执行 |
| **发现 (Finding)** | 一条结论（题号 / 答案 / 置信度 / 证据） |
| **步骤 (Step)** | 一次可重放的操作（命令 + 参数 + 结果） |

## 四、下钻机制（三层，全场通用）

```
L1  视图层      我看到"数据回灌卡在推送文件"
                │  [复制命令] 或 Alt+点击
                ▼
L2  命令层      adb -s 127.0.0.1:16385 push "...\notevault.db" /data/data/.../databases/
                │  [在终端中运行] [查看原始输出]
                ▼
L3  原始层      push: Permission denied
                （未经处理的 stdout / stderr 全文）
```

实现约定：

- 每个卡片/行/节点右下角都有 `⌘` 按钮 → 弹 L2
- `Alt + 点击` 直接开终端并预填命令（不自动执行）
- L3 永远保留环形缓冲（默认 5 万行），可搜索、可导出

## 五、命令录制与回放（Recorder）

每次可视化操作自动生成一条 **Step**：

| 字段 | 例 |
|---|---|
| 序号 | 12 |
| 动作 | 推送文件 |
| 等价命令 | `adb -s … push … ` |
| 参数 | 源、目标、预期 md5 |
| 结果 | ✖ Permission denied |
| 耗时 | 0.8s |

导出的三种形态：

| 形态 | 用途 |
|---|---|
| `.ps1` / `.sh` | 用户自己重跑（用户习惯：脚本自己跑） |
| `.md` 教程 | 直接进笔记：命令 + 输出 + 截图位（写作场景） |
| `.json` | 给别的工具消费 / 回归测试 |

**回放**：按顺序重跑，可设"到第 N 步停"。这条直通一个真实需求 —— **把打过的一仗重新打一遍**（原来的经验是：只有亲手打过的仗才写得出细节）。

## 六、交互原则（五条）

| # | 原则 | 具体表现 |
|:--:|---|---|
| 1 | **键盘优先** | `⌘K` 命令面板收录所有动作；视图切换 `1~6`；无需鼠标可完成全流程 |
| 2 | **一切可复制** | 任何操作都有「复制为命令」，且按当前 OS 出对应方言（痛点 D4） |
| 3 | **颜色不独担信息** | 状态同时用**灯形 + 文字 + 计数**，色盲可读 |
| 4 | **失败不静默** | 自动恢复必须在界面上留下一条事件（如"forward 已自动重建"） |
| 5 | **不替用户做结论** | 差分矩阵给"候选结论"，拓扑给"⚠断链"，都要人点确认 |

## 七、深色 / 浅色

两套主题都要有（长时间盯屏）。约束：

- 状态色在两套主题下**语义一致**（绿永远是"有证据的通过"），只调明度，不改色相
- 差分矩阵的高亮色不参与主题切换逻辑，保持固定（它是"注意力标记"，不是"状态"）
- 原始终端默认深色（终端天然深色），可跟随主题

## 八、可用性验收（写进 08 的验收用例）

| 编号 | 验收点 |
|---|---|
| UI-1 | 从空白启动到「设备已连接」，全程不打开终端，且每一步都能说出"它凭什么判定通过" |
| UI-2 | 任意一次探针触发，能在 2 次点击内拿到等价 frida 命令 |
| UI-3 | 一次受控实验：追加一组输入 → 看到变异度列更新 → 得到结论候选，全程不写一行 JS |
| UI-4 | 拓扑视图能正确圈出"来源未定位"的边（用 `NoteVault_DB_SecureKey_2024` 的真实案例验） |
| UI-5 | 一次运行可一键导出成既能 `bash` 跑、又能直接粘进笔记的两种形态 |
