# 05 · 诊断知识库

> 这是 lovelyfrida 的**灵魂**。工具会不会用，取决于它能不能在出错时说清楚「你踩的是哪个坑」。

全部 48 条规则都来自实战，标注了出处。格式统一：**症状（可匹配）→ 真因 → 处置**。

---

## 一、规则引擎设计

### 1.1 三条触发路径

| 路径 | 说明 | 例 |
|---|---|---|
| **被动匹配** | 输出流命中特征（正则 / 谓词） | `push: Permission denied` |
| **状态谓词** | 不依赖报错，看状态组合 | 探针装载成功 **且** 命中 0 次 |
| **主动探测** | 定时/事件后主动查一次 | 每 30s 校验 `adb forward --list` 是否还在 |

**第二条和第三条最重要。** 动态分析里最贵的错误是**没有报错的那种错误**：钩子挂上了、命令返回 0、程序在跑 —— 但什么也没发生。

### 1.2 规则结构

| 字段 | 说明 |
|---|---|
| ID | `E-01` 这类，分组前缀见下 |
| 严重度 | 阻断（流程走不下去）/ 警告（能继续但有隐患）/ 提示 |
| 匹配器 | 正则 / 状态谓词 / 主动探测 |
| 真因 | 一段话，讲机制，不讲现象 |
| 处置 | 有序动作列表，**可一键执行** |
| 出处 | 哪次实战、哪份文档 |

### 1.3 分组前缀

| 前缀 | 域 | 条数 |
|:--:|---|:--:|
| `E` | 环境与连接 | 8 |
| `S` | 会话（frida-server / forward / 注入进程） | 7 |
| `P` | 挂钩与类加载 | 8 |
| `O` | 观测与数据呈现 | 5 |
| `D` | 数据回灌 | 7 |
| `C` | 加密库与算法 | 8 |
| `X` | 邻域（同一工作流里会撞上的其它工具） | 5 |

## 二、E · 环境与连接（8 条）

| ID | 症状（可匹配） | 真因 | 处置 |
|:--:|---|---|---|
| **E-01** | `adb devices` 输出只有标题行 | 模拟器没启动 / 未开调试 / 端口不对 | ① 确认模拟器已启动 ② 扫端口 `{16384,16385,7555}` ③ 逐个人工试连 |
| **E-02** | `adb connect` **长时间无输出、不返回** | 连到了非 adbd 端口（如 `5555`），TCP 通但没有协议应答 | **必须加 15s 硬超时**；换端口重试；把"试过哪些端口"列出来 |
| **E-03** | `adb devices` 显示 `<serial> offline` | 模拟器刚起，adbd 未就绪 | `disconnect` → 等 2s → 重连，最多 5 次；全部失败才报错 |
| **E-04** | 找不到 adb / 系统 adb 版本老 | 系统 adb 与模拟器 adbd 协议不匹配 | 用**模拟器自带**的 `adb.exe`（如 `MuMuPlayer-12.0\shell\adb.exe`）；UI 显示候选清单及其版本 |
| **E-05** | `error: more than one device/emulator` | 同时连了多台 | 一律带 `-s <serial>`；UI 里选中哪台，命令里就带哪台 |
| **E-06** | `adb shell id` 不含 `uid=0(root)` | adbd 未提权 | `adb root`（会重启 adbd，等 3s 重连）；仍不行则检查模拟器设置里是否开了 ROOT |
| **E-07** | 灌完数据 App 仍读不到；或 `restorecon: not found` | SELinux 标签不对（`Enforcing` 模式）；老 Android 无 restorecon | `Enforcing` 时 `restorecon -R` 必做；`Permissive` 可跳过；`not found` 属正常，不阻断 |
| **E-08** | 推了 frida-server 后启动即崩 / `Exec format error` | ABI 不匹配（给 `x86_64` 推了 `arm64` 包） | 先查 `getprop ro.product.cpu.abi`，再选包（`x86_64` / `arm64-v8a`） |

## 三、S · 会话（7 条）

| ID | 症状（可匹配） | 真因 | 处置 |
|:--:|---|---|---|
| **S-01** | `failed to connect to remote frida-server` / `unable to connect to remote frida-server` | **客户端与设备端 frida-server 版本不一致** | 三处版本对照（客户端 / 内置矩阵 / 设备端）；推送匹配版；重启 server |
| **S-02** | `frida-ps -H 127.0.0.1:27042` 连接被拒 | 没有 `adb forward` | `adb -s <serial> forward tcp:27042 tcp:27042`；检查 `adb forward --list` |
| **S-03** | server 起来能连，过一会儿就断了 | frida-server 是**前台进程**，`adb shell` 通道断（窗口关闭/SSH 断开）就被 SIGHUP 杀 | 会话托管为常驻任务（后台 + disown / supervisor）；断连自动重启并留痕 |
| **S-04** | 端口占用、server 起不来 | 设备端有残留旧 frida-server 进程 | 启动前 `pkill -f frida-server`，等 1s 再起；记录清理的 PID |
| **S-05** | 命令"启动成功"但 `frida-ps` 连不上 | **假绿灯**：进程起了但没在监听（崩溃/端口被改） | 独立验证：`adb shell "ss -tlnp \| grep :27042"`；"声称启动"与"实测监听"必须分开表示 |
| **S-06** | 本机 27042 被占 | 本机别的程序占了这个端口 | 换端口（`27043`…），forward 跟着换；UI 显示端口占用者 |
| **S-07** | spawn 模式 App 卡白屏 / 起不来 | frida 的 spawn 挂起等待注入，注入脚本报错导致进程一直停着 | 用 attach 模式代替；或修正脚本；确认 `attach` 目标进程确实存在 |

## 四、P · 挂钩与类加载（8 条）

| ID | 症状（可匹配） | 真因 | 处置 |
|:--:|---|---|---|
| **P-01** | `Java.use(...)` 抛错 / `java.lang.ClassNotFoundException` | 类名错（混淆 / 内嵌类用 `$` / 类在别的 dex） | 用静态分析核对类名；内嵌类用 `Outer$Inner`；确认 dex 已加载 |
| **P-02** | 挂钩时 `C.method === undefined` | 方法名错，或该方法在这个类**没有**（继承来的要往上找） | 打印类的全部方法 `C.class.getDeclaredMethods()` 做核对 |
| **P-03** | 给 `.implementation` 赋值时报重载歧义 | 同名方法有多个签名 | 遍历 `.overloads.forEach(...)`；工具默认自动展开 |
| **P-04** | 挂构造函数无效 | 构造函数在 frida 里叫 `$init`，不是 `<init>` 或类名 | 用 `C.$init.overloads.forEach(...)`；对象建成后立刻 dump 字段 |
| **P-05** | 脚本执行时**静默无输出**，过一会儿才正常 | **frida 17.x 类加载时序**：脚本跑得比类加载快 | 延迟注册（包装在定时器里）+ 失败重试；工具自动处理（不再手写 `setTimeout(...,3000)`） |
| **P-06** | 日志里只有 `skip xxx: not found` | `try/catch` 把类缺失吞了 | 每个探针独立三态上报：**已装载 / 类缺失 / 挂载失败**；不要一个 catch 了事 |
| **P-07** | `Java.perform` 里的代码"没执行" | 目标不是 Java 层进程（纯 native）或 `Java` 对象不可用 | 确认目标 App 有 Java 层；纯 native 目标改用 native 探针 |
| **P-08** | 注入即崩 / App 立刻退出 | **反调试 / 反 frida 检测** | 这是对手的领域，不在本工具能力内；工具只负责**明确告诉你是这个原因**（特征：注入后进程立刻消失 + 无异常日志） |

## 五、O · 观测与数据呈现（5 条）

| ID | 症状（可匹配） | 真因 | 处置 |
|:--:|---|---|---|
| **O-01** | 参数打印成 `[B@1a2b3c` / `Ljava.lang.Object;@…` | 没有对 `byte[]` / 对象做格式化 | 参数格式化器选 `byte[]hex`（并截断，如 64 字节）；这是填表选项，不该写代码 |
| **O-02** | 日志刷屏、UI 卡死 | 大对象 / 高频调用未经截断 | 格式化器带长度上限（默认 128）；超限 `…(+N)`；事件分层（原始输出按需拉取） |
| **O-03** | ★ 探针**装载成功但命中 0 次** | 目标逻辑没被执行 —— 最常见的是 **App 带着登录态直接进主页，根本没走登录分支** | ① 检查 prefs/配置里的登录态键，清掉 ② 确认入口手势走对 ③ 确认是 `spawn` 而不是 attach 到了错误的进程 |
| **O-04** | 找不到某个功能入口 | **隐藏手势**：长按 1.2s 才触发（单击/双击/三连点都无反应）；Flutter 界面无可枚举控件 | 依次试：单击 → 双击 → 长按(1s/1.2s/2s) → 三连点 → 角落坐标（右上/左上）；成功后**把坐标记进应用档案** |
| **O-05** | 只能看纯文本日志，无法比对 | 用 `console.log` 拼字符串，丢掉了类型 | 结构化：agent `send()` JSON；宿主不做文本正则（这是本工具的核心设计决策，见 02 章 §3.2） |

## 六、D · 数据回灌（7 条）

| ID | 症状（可匹配） | 真因 | 处置 |
|:--:|---|---|---|
| **D-01** | `adb push: Permission denied` | adbd 非 root，或目标目录属主/权限不符 | ① 先 `adb root` 重连 ② 走中转：push 到 `/data/local/tmp/` → `su -c 'cp … && chown …'` |
| **D-02** | `su: invalid option -- a` | `su -c "…"` 用双引号，被 shell 拆包 | **只能单引号**：`su -c 'cmd1; cmd2'`；命令构造层统一处理 |
| **D-03** | 灌完 App 启动**闪退** | `chown` 的 uid 填错，或目录属主不对 | 从 `pm list packages -U` 取真实 uid（本项目实测 10042 / 10043）；重新 `chown -R <uid>:<uid>` |
| **D-04** | `restorecon: not found` | 老 Android 无此命令 | 非阻断。`getenforce` 是 `Permissive` 时可忽略 |
| **D-05** | 文件明明在，App 却当没有 | SELinux 标签未刷 / 属主不对 / App 有完整性校验 | 先 `restorecon -R`；再核对 uid；仍不行则怀疑 App 有校验（转静态分析） |
| **D-06** | 灌入的内容被改回去了 | App 正在运行，写回了自己的状态 | 灌之前必须 `am force-stop <pkg>`；工具把"停应用"设为不可跳过的一步 |
| **D-07** | `mkdir` 出来的目录属主不对 | 目录是手工建的，属于 root | 先**空跑一次**让 App 自己把目录结构建出来，再覆盖内容 |

## 七、C · 加密库与算法（8 条）

| ID | 症状（可匹配） | 真因 | 处置 |
|:--:|---|---|---|
| **C-01** | DB Browser 报 `file is not a database`，**不弹密码框** | 文件不是明文 SQLite —— 头 16 字节是随机盐（SQLCipher） | 读头 16 字节判定：`53 51 4c 69 74 65 20 66 6f 72 6d 61 74 20 33 00` = 明文 SQLite；否则走 SQLCipher 路径 |
| **C-02** | `sqlcipher` 命令行用同一口令报 `encrypted-or-not-a-database` | CLI 与 python 绑定的 PRAGMA 处理路径不同 | **用 python 绑定**（`sqlcipher3`）；CLI 这条路记进知识库，不要再试 |
| **C-03** | 口令对但开不了库 | SQLCipher 兼容档不同（KDF 迭代/算法/页大小） | 穷举组合：`cipher_compatibility=4` / `=3` + `kdf_iter`(64000/256000) + `hmac_algorithm`(SHA1/SHA256/SHA512) + `kdf_algorithm` |
| **C-04** | ☠ 库打开后数据变了 / 打不开了 | **SQLCipher 库一被写就重新加密**；或工具写坏了检材 | 只读挂载（`:ro`）或先复制到工作区；本工具的只读保护是**拒绝写**，不是警告 |
| **C-05** | 找不到库口令 | 口令存放位置因 App 而异，且可能是**编码值** | 两个已知形态：① `shared_prefs/*.xml`（可能明文）② `app_flutter/files/password.json`（可能要 `[1:-2]` 变换）；仍找不到就挂钩 `SQLiteDatabase.$init` 抓 |
| **C-06** | 通用爆破器报 "no such mode" | 算法不是标准组合（如**链式十六进制 SHA-256 迭代 10000 轮**） | 从算法规格书生成专用爆破器骨架（C）；用预置填充块 + `SHA256_Transform` 消掉填充开销；需 `-O3 -march=native -fopenmp` |
| **C-07** | 自写爆破器跑完全空间**无命中** | 自己的实现与实际算法**不等价**（差一个编码层、差一次迭代） | **先用已知明文自测**：拿一个已知 (明文, 目标值) 跑一遍，逐字节比对；不通过就改实现，绝不进入全量爆破 |
| **C-08** | 明文算得出哈希但开不了库 / 反之 | 编码层数不同（hex 几层 / base64 / 原始字节） | 逐层列出编码链；分别验证"数学等价"与"功能可用"两条（这正是原则 5 的双证据） |

## 八、X · 邻域（5 条，同一工作流会撞上）

| ID | 症状（可匹配） | 真因 | 处置 |
|:--:|---|---|---|
| **X-01** | 一个 `.db` 文件，DB Browser 打不开，也不是 SQLCipher | 可能是 **bbolt**（etcd 存储）—— 魔数 `ED 0C ED DA` | 不用 GUI：`strings -a -n 8 db`；键值都是明文（如 `/registry/configmaps/shop/...`）。要 GUI 用 `boltbrowser` |
| **X-02** | 从二进制里 `strings` 出来的内容**莫名其妙被截断** | `strings` 只输出 ASCII 可打印字符，**UTF-8 中文一个字节都不留**，且不报错 | 按字节无损读：Latin-1 转字符串后正则，再按 UTF-8 还原；整套命令见项目手册 |
| **X-03** | 用 PowerShell `>` 重定向后文件体积翻倍 | PS 5.1 的 `>` 默认写 **UTF-16** | 用 `Set-Content -Encoding UTF8` / `Out-File -Encoding utf8` |
| **X-04** | MySQL 8.0 拒绝启动：`MY-010159` + `MY-011087` + `MY-010020` | datadir 放在 NTFS/9p 上，`lower_case_table_names` 被探测成 2，与数据字典里的 0 冲突（**不是版本问题**） | datadir 搬进 Linux 端卷（`docker volume create` + `busybox cp -a`）；**别浪费时间换版本** |
| **X-05** | MySQL 8.0 里 `SHOW TABLES` 返回 `Empty set`，**不报错** | 8.0 起 `.frm` 元数据已并入 InnoDB 数据字典，**静默忽略** 5.x 的 MyISAM 表 | 换 `mysql:5.7`；这也说明"没有报错"不等于"没问题" |

## 九、诊断卡片的形态

```
┌─────────────────────────────────────────────────────────────┐
│ ⚠ O-03  探针装载成功，但命中 0 次                    [忽略]  │
│                                                             │
│ 真因                                                         │
│   目标逻辑没有被执行。最常见的原因是 App 带着登录态直接进了    │
│   主页，根本没走登录分支 —— 所以 hashPassword 从未被调用。    │
│                                                             │
│ 处置（按可能性排序，可一键执行）                              │
│   ① 扫描并清空 prefs 中的登录态键                          ▶ │
│   ② 确认入口手势走对（本应用需长按右上齿轮 1.2s）           ▶ │
│   ③ 确认 attach 到了正确进程                                ▶ │
│                                                             │
│ 出处  2026 盘古石杯决赛 · WP §5 · 复盘手册阶段 5 注           │
└─────────────────────────────────────────────────────────────┘
```

三条渲染要求：

1. **先真因，后处置** —— 只给处置就成了"玄学试错清单"。
2. **处置按可能性排序**，且可一键执行、执行结果回到同一条卡片上。
3. **必须带出处** —— 让用户能自己去核对（原则 2 的精神）。

## 十、规则的维护流程

| 步骤 | 要求 |
|---|---|
| 1. 新坑出现 | 先记进当日记忆（症状 + 真因 + 处置 + 出处） |
| 2. 可匹配化 | 把症状写成**正则或状态谓词**，不能是"感觉不对" |
| 3. 定严重度 | 阻断 / 警告 / 提示 |
| 4. 写出处 | 哪次实战、哪份文档、哪一行 |
| 5. 回归 | 用历史案例当测试集：每条规则至少要能被一个真实场景触发 |

**反面基准**：知识库里不允许出现「重启试试」这种没有真因的规则。**没有机制解释的处置不是诊断，是迷信。**

## 十一、与 01 章的对应关系

01 章的 33 条痛点 = 需求侧；本文件的 48 条规则 = 实现侧的落地形态。二者交叉覆盖，多出来的部分是把痛点在实现层拆得更细（例如 E2 在 01 里是一条，在这里拆成 E-02 端口 + E-03 offline + E-05 多设备）。
